# secure.abramov.vip — план разработки

Дата: 22 октября 2026 года.
Статус: проектное техническое задание; предложенные решения требуют проверки при реализации.

## 1. Концепция

Публичный многоязычный радар IT-безопасности и проблем обновлений для системных и сетевых администраторов.

Основной вопрос: что произошло, затронута ли моя инфраструктура и что проверить или предпринять?

Языки: русский, немецкий, английский (RU / DE / EN).

Основные направления:
- Уязвимости: CVE, затронутые версии, исправления, подтверждённая эксплуатация.
- Атаки и инциденты: подтверждённые кампании, компрометации, утечки.
- Проблемные обновления: регрессии, несовместимости, отозванные релизы, ошибки установки.

Не обещать охват «всех возможных источников». Публиковать прозрачный каталог покрытия и состояние сбора.

## 2. Отличие от существующих сервисов

Существуют OpenCVE, Feedly CVEs и специализированные официальные ресурсы вроде Windows Release Health. Проект не является первым агрегатором уязвимостей. Точное совпадение всей предлагаемой комбинации функций не установлено.

Позиционирование:
> Что уязвимо, что уже атакуют и какие обновления могут сломать инфраструктуру — кратко, с источниками и на трёх языках.

Отличия:
- Безопасность и эксплуатационные проблемы в одной ленте.
- Полноценные RU / DE / EN версии.
- Практические карточки для администратора.
- История развития события.
- Инфраструктурный фокус.
- Явное разделение подтверждённых фактов и предварительных сообщений.

Не разрабатывать ещё один полный каталог CVE ради количества страниц.

## 3. Источники

### 3.1. Первая очередь

- CISA KEV: известная эксплуатация, JSON/CSV.
- NVD API: CVE и изменения записей.
- Windows Release Health: известные проблемы обновлений и устранение.
- Официальные security advisories, release notes и status pages производителей.

Кандидаты на покрытие: Microsoft, Cisco, Fortinet, Palo Alto, Ivanti, Broadcom/VMware, Proxmox, OPNsense, Ubuntu, Debian, Red Hat, Docker, Kubernetes.

Для каждого кандидата отдельно проверяются доступные форматы, правила использования и техническая возможность подключения.

### 3.2. Дополнительные источники

Профильные издания и исследователи используются для обнаружения и контекста. GitHub Issues, форумы и сообщества — для ранних сигналов, прежде всего по регрессиям.

Одна жалоба не является подтверждением массовой проблемы.

### 3.3. Каталог источников

Поля:
- ID, название, URL, тип источника.
- Производители, продукты, язык.
- Формат: API / RSS / HTML.
- Период опроса.
- Время последней успешной проверки.
- Cursor/watermark, ETag/Last-Modified при поддержке.
- Контрольная сумма.
- Состояние ошибок.
- Условия использования и атрибуции.

## 4. Автоматизация

```text
RSS / API / официальные страницы
              ↓
GitHub Actions: сбор и сохранение изменений
              ↓
Нормализация → дедупликация → объединение в события
              ↓
Извлечение и проверка фактов
              ↓
Подготовка базовой статьи → перевод RU / DE / EN
              ↓
Валидация → сборка → деплой
              ↓
Проверка опубликованной страницы
              ↓
Telegram / RSS / Web Push
```

Предлагаемый интервал основных сборщиков: 30 минут. Это целевая настройка, не гарантия точного времени доставки.

GitHub Actions может запускаться с задержкой или пропускать расписания. Обработка должна продолжаться от последнего успешного состояния, а не брать только фиксированное последнее окно.

Предусмотреть ручной запуск, контроль параллельности, повторные попытки и внешний мониторинг последнего успешного сбора.

## 5. Дедупликация и история

Разделить:
1. Исходное сообщение.
2. Событие.
3. Публикацию события на конкретном языке.

Ключи сопоставления: CVE, advisory ID, KB, производитель, продукт, версия, тип события, URL, сходство заголовка и время.

Не объединять всё исключительно по CVE: эксплуатация старой уязвимости и выпуск патча могут быть разными событиями.

Сохранять исходные ссылки, даты обнаружения и изменения, версии материала и причины существенных обновлений.

Жизненные циклы различаются по типам событий. Пример: обнаружено → подтверждено → исправление доступно → устранено.

Повторные уведомления отправлять только о существенных изменениях: новая эксплуатация, отзыв патча, изменение затронутых версий, появление исправления.

## 6. Модель данных

Минимальные сущности:
- Source: источник и настройки адаптера.
- SourceItem: полученное сообщение и его метаданные.
- Event: единое событие со стабильным ID.
- ArticleTranslation: локализованный материал.
- EventRevision: история изменений.
- DeliveryJob: задание доставки и статус.
- PushSubscription: подписка и предпочтения.
- SourceSuggestion: предложение источника и связанный Issue.
- AnalyticsAggregate: агрегированные просмотры.
- ActiveSession: краткоживущая активная сессия.

Поля Event:
- Стабильный ID, категория, производитель, продукты.
- CVE/advisory/KB и затронутые версии.
- CVSS с источником и версией шкалы, если доступен.
- Признаки KEV/эксплуатации с доказательствами.
- Редакционный приоритет отдельно от CVSS.
- Статус подтверждения, исправления и обходного решения.
- Даты события, публикации и изменения.
- Связанные источники.

## 7. ИИ и переводы

ИИ используется для краткого пересказа, классификации, извлечения полей, заголовков и перевода. Он не является самостоятельным источником фактов.

Запрещено додумывать версии, CVSS, эксплуатацию, исправленные сборки, команды и сроки установки патчей.

Процесс:
1. Извлечение фактов в JSON.
2. Привязка существенных фактов к источникам.
3. Проверка схемы и обязательных полей.
4. Подготовка базового материала.
5. Перевод на два других языка.
6. Проверка неизменности CVE, KB, URL, версий и команд.

Входящие документы считать недоверенными данными. Инструкции внутри источников не должны управлять workflow или моделью.

При ошибке материал остаётся в очереди, а не публикуется любой ценой.

### 7.1. Бесплатные варианты

| Вариант | Назначение | Ограничения |
|---|---|---|
| Gemini API Free Tier | Перевод, суммаризация, классификация | Бесплатность и квоты зависят от модели и проекта; проверить актуальные условия обработки данных |
| DeepL API Free | Специализированный перевод | По проверенной справке: до 500 000 символов в месяц |
| Google Cloud Translation | Специализированный перевод | Для стандартного NMT первые 500 000 символов покрываются ежемесячным кредитом; сверх лимита платно |

Это API, а не бесплатные чат-интерфейсы. Наличие бесплатного тарифа не означает неограниченную производственную нагрузку.

Для Gemini проверять условия использования контента бесплатного уровня; не передавать секреты и внутренние документы без отдельной оценки.

### 7.2. Предварительный выбор

Для прототипа: Gemini API при доступности подходящей бесплатной модели и квоты. DeepL — альтернативный переводчик.

Провайдер должен быть заменяемым. Кеширование по хешу текста, языку, версии промпта и модели. Дедупликация выполняется до вызова ИИ.

Исчерпание квоты: очередь и повторная обработка. Платный fallback не включать автоматически без заданного бюджета.

Перед выбором провести тест 30–50 реальных материалов: точность терминов, сохранность идентификаторов, качество RU/DE/EN, расход и задержка.

Пример оценки DeepL: базовый текст 2 000 символов × два целевых языка = около 4 000 символов расхода на заметку. Лимит 500 000 — примерно 125 заметок в месяц без повторных переводов и дополнительных полей. 20 таких заметок в день за 30 дней — около 2,4 млн символов.

## 8. Структура сайта и индексация

```text
/ru/                       /de/                       /en/
/ru/news/<stable-id>-<slug>/
/de/news/<stable-id>-<slug>/
/en/news/<stable-id>-<slug>/
/ru/products/opnsense/
/ru/topics/update-issues/
/ru/archive/
/ru/rss.xml
/de/rss.xml
/en/rss.xml
```

Требования:
- Отдельный URL и полноценный HTML для каждого языка.
- Переведённые текст, заголовки и метаданные.
- Корректные lang, hreflang и self-canonical.
- Sitemap.
- Переключение языка на эквивалент той же статьи.
- Стабильные URL; при смене slug — перенаправление.
- Незавершённые переводы не индексируются.
- Статья читается без JavaScript.
- Пагинация доступна обычными ссылками.

Индексация поисковиками не гарантируется. Ценность — собственное структурирование и контекст, а не массовое создание переводных страниц.

## 11. Telegram, RSS и Push

### Telegram

Три языковых канала. Сообщение: приоритет, тип, заголовок, затронуто, статус, подтверждённое действие, ссылка.

Отправка после деплоя и проверки URL. Повторная отправка только при существенном изменении. Позже — бот с персональными фильтрами.

### RSS

Отдельные RU / DE / EN ленты. Стабильный GUID при редактировании. Позже — категории и продукты.

### Web Push

Небольшой API для приёма подписок, хранения endpoint/ключей, отправки и удаления недействительных подписок.

Настройки: язык, минимальный приоритет, категории, продукты, режим уведомлений. Разрешение запрашивается после явного действия пользователя.

Для iOS/iPadOS учесть требования Home Screen web app и поддерживаемые версии. Не обещать одинаковую работу во всех браузерах.

## 12. Предложение источников через GitHub Issues

Кнопка: «+ Предложить источник».

Поля формы:
- Название — обязательно.
- URL сайта/RSS/API — обязательно.
- Тип источника — обязательно.
- Язык — обязательно.
- Продукты и тематика — необязательно.
- Обоснование — необязательно.
- Документация API/RSS — необязательно.

Варианты:
1. MVP: переход в GitHub Issue Form; отправка через GitHub-аккаунт.
2. Целевой: форма на сайте → серверная функция → GitHub API. Посетителю не нужен GitHub-аккаунт.

```text
Форма → валидация → антиспам/rate limit → проверка дублей
      → Issue в фиксированном репозитории → номер и ссылка
```

Заголовок: `[Source suggestion] Название источника`.
Метки: source-suggestion, needs-review, accepted, duplicate, rejected.

Репозиторий и метки задаются сервером. Токен только на серверной стороне, с минимальными правами.

Issue не включает источник автоматически. Проверка происхождения, условий, формата, тестового сбора — до принятия.

Не загружать произвольные URL из привилегированного workflow. Защитить проверяющие компоненты от SSRF и доступа к внутренним адресам.

Перед отправкой предупредить о публичности Issue и запрете конфиденциальных данных. Контакты посетителя не требуются.

## 13. Ko-fi

Обычная стилизованная ссылка предпочтительнее загружаемого на каждой странице платёжного виджета.

Размещение: шапка/меню, подвал, ненавязчивый блок после статьи.

Тексты:
- RU: «Поддержать проект».
- DE: «Projekt unterstützen».
- EN: «Support the project».

Без перекрытия текста и навязчивых попапов. Адрес страницы Ko-fi задаётся в конфигурации.

## 14. Просмотры и онлайн

Публичная компактная статусная панель, не рекламный баннер.

Определения:
- Просмотры сегодня: зарегистрированные открытия за сутки UTC.
- Всего просмотров: зарегистрированные открытия с запуска счётчика.
- Просмотры статьи: сумма трёх языковых версий по Event ID.
- Активные сессии: приблизительное число активных браузерных сессий за последние 2 минуты.

Не называть сессии точным числом людей.

Реализация:
- Регистрация открытия.
- Heartbeat раз в 45–60 секунд, только для видимой вкладки.
- Краткоживущий случайный идентификатор сессии.
- Истечение активности через 2 минуты.
- Агрегированный публичный endpoint с коротким кешем.
- Rate limiting и разумное исключение ботов.
- Без fingerprinting и постоянного идентификатора.
- Не хранить IP в прикладной таблице; отдельно проверить инфраструктурные логи.

Статистика приблизительная, возможны блокировки скриптов и накрутка. Методика публикуется на сайте.

Внутренняя аналитика владельца — отдельно, например Cloudflare Web Analytics. Не предполагать, что она автоматически предоставляет нужный публичный онлайн-виджет.

## 15. Архитектура и стек

| Компонент | Предварительный выбор |
|---|---|
| Сайт | Astro + TypeScript |
| Дизайн | Собственные компоненты и CSS-переменные |
| Сбор | Python |
| Валидация | Pydantic / JSON Schema |
| Автоматизация | GitHub Actions |
| Публикуемый контент MVP | Структурированные JSON-файлы |
| Поиск | Локальный статический индекс |
| Размещение | Статический хостинг/CDN |
| Интерактивный API | Небольшой serverless-сервис |
| Подписки и доставка | Небольшая SQL-база |
| Перевод | Заменяемый API-провайдер |

```text
Статический сайт + GitHub Actions
                └── API
                     ├── Предложения → GitHub Issues
                     ├── Счётчики и активные сессии
                     └── Push-подписки и доставка
```

GitHub Actions не используется как обработчик каждого посещения или отправки формы.

Персональные подписки, секреты и журналы отправки не хранятся в публичном репозитории. Нужны резервные копии постоянного состояния. Actions — исполнитель, не единственное постоянное хранилище.

## 16. Надёжность и безопасность

- Минимальные права workflow и API.
- Secrets для ключей, отсутствие секретов в логах.
- Фиксация сторонних Actions по commit SHA.
- Контроль зависимостей.
- Таймауты, retries/backoff, лимиты размера документов.
- Защита от одновременных запусков.
- Санитизация HTML и защита от XSS.
- Ограничения исходящих запросов и защита от SSRF.
- Недоверенные данные не исполняются как код.
- Журнал ошибок и карантин материалов.
- Outbox для заданий доставки.
- Идемпотентность повторных запусков и учёт частично успешных отправок.
- Возможность остановить рассылку, снять материал и откатить деплой.
- Внешняя проверка давности последнего успешного сбора.
- Раздельные права публичной формы и публикационного конвейера.

## 17. Этапы реализации

### Этап 1. Спецификация
- Схема данных и правила подтверждения.
- Первые 10–15 источников.
- Проверка API и условий использования.
- Макеты и языковые маршруты.
- Репозиторий, размещение, API и бюджет.

### Этап 2. Сайт на тестовом контенте
- Консольная лента и отдельные статьи.
- RU/DE/EN, фильтры, RSS, sitemap.
- Адаптивность и доступность.
- Ko-fi и ссылка на предложение источника.

### Этап 3. Сбор
- Адаптеры, состояние, дедупликация.
- История изменений и повторные запуски.
- Мониторинг и обработка ошибок.

### Этап 4. ИИ
- Тест 30–50 материалов.
- Извлечение фактов и перевод.
- Контроль идентификаторов и очередь ошибок.
- Квоты и кеширование.

### Этап 5. Публикация и Telegram
- Деплой и проверка URL.
- Три канала, outbox, дайджест.
- Значимые обновления без дублирования.

### Этап 6. Интерактивные функции
- Форма на сайте → Issue.
- Счётчики просмотров и активности.
- Push и управление подписками.
- Быстрый просмотр, страницы продуктов.

## 18. Границы MVP

Включить:
- 10–15 проверенных источников.
- Три языка.
- Отдельные страницы статей.
- Основные фильтры и поиск.
- RSS и Telegram.
- Ko-fi.
- Предложение источника хотя бы через GitHub Form.
- Простые счётчики, если готов API; их сбой не блокирует публикацию.

Отложить: сложные персональные профили, обширный каталог CVE, сотни источников, сложную CMS, Kubernetes, продвинутые панели аналитики.

## 19. Приёмочные критерии

- Несколько источников одного события не создают лишних публикаций.
- Каждая статья содержит проверяемые источники.
- Три версии связаны; CVE/KB/версии совпадают.
- Незавершённые переводы не публикуются как готовые.
- Повторный запуск не дублирует доставку.
- Пропущенный запуск не теряет накопившиеся события.
- Сбой источника не останавливает весь сбор.
- Изменения сохраняют историю и стабильный адрес.
- Лента и статьи читаются без JavaScript.
- Мобильный интерфейс не имеет горизонтальной прокрутки.
- Видно время последнего успешного сбора.
- Предложение создаёт ровно один Issue; ошибки и дубли объясняются посетителю.
- Онлайн обозначен как оценка активных сессий.
- Отказ статистики не ломает сайт.
- Секреты и подписки не попадают в публичный репозиторий.

## 20. Решения перед стартом

- Выбрать репозиторий и его публичность.
- Определить хостинг, API и базу состояния.
- Подтвердить первые источники и приоритетные продукты.
- Выбрать модель после проверки квот и теста качества.
- Задать лимит расходов и правила остановки.
- Создать Telegram-каналы и Ko-fi страницу.
- Уточнить обработку данных, сроки хранения, уведомления о конфиденциальности и необходимые юридические страницы для фактической модели эксплуатации.
